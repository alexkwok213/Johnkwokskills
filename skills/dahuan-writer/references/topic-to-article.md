# 从命题到文章

适用于新命题、选题策划与整篇重构。沿用现有稿件改标题、裁图或修一句话时，不重新走全流程。它提供判断顺序，不要求每次生成一套表格，也不增加固定的用户审批环节。

## 先看问题，再扫描资料与案例

先从用户的话里确定：这次发布或变化是什么，主要读者是谁，读完要能解释、选择还是实际完成一件事。标题、立场和交付形式已经明确时先保留。拿不准但不影响研究的内容，可以带着假设继续；会改变整篇方向的缺口再问。

随后做一轮资料与案例扫描。先读用户提供的原文、视频或文档，再找官方发布、帮助文档和可核实的实际案例。产品能力、接入条件、版本、价格、资格等易变化信息要核对当前一手资料。用户视频可作为该演示内容的证据，不能自动证明所有账号都已开放。

在 OPCroad 项目中选一两篇最相近的较新稿，学习读者视角、解释深度和用户改法。不机械读取全部历史版本，也不把旧稿中的数字、产品状态或亲历搬到新稿里。

这一轮要有足够材料比较角度：具体新变化、几个可见用途、可用案例和图片、还不能支持的主张。已有材料充足就继续，不为凑来源数量无限搜索。选定角度后，再针对缺口补查。

## 文类与案例来源分开选择

| 文章的主目的 | 读者读完应得到什么 | 常见推进方式 |
|---|---|---|
| 新产品或功能科普 | 说清是什么、能替自己做什么、从哪里开始 | 新变化或代表结果 → 按任务解释用途 → 组合用法 → 接入与关键条件 |
| 实操教程或体验 | 能照着完成一项任务，知道结果与投入 | 任务与成果 → 准备条件 → 输入和关键操作 → 输出检查 → 适用范围 |
| 案例拆解与做法借鉴 | 理解谁遇到什么问题、怎样完成、哪些方法可迁移 | 需求 → 行动 → 成果与成本 → 有根据的判断 → 读者可尝试的一步 |
| 能力变化与观点观察 | 理解一组事件共同说明什么，为什么与自己有关 | 有辨识度的变化 → 相关案例推进 → 必要解释或对照 → 判断与选择 |

自己的知识库、技能或资源发布，也先按读者目标处理：介绍价值、教人使用、分享实践可以各有侧重。表格是选角度的工具，正文不必把这些栏目逐个写出来。

| 案例从哪里来 | 可以怎么用 | 不能越过的边界 |
|---|---|---|
| 大欢本人实测或用户确认的经历 | 写真实需求、提示、AI 动作、人的投入和可见成果 | 不补造耗时，不把单次成功扩大为长期稳定，不用简单样本证明复杂任务 |
| 官方演示或教程 | 直接用任务与结果解释功能，提取产品界面；来源与时间点保存于素材记录 | 不冒充本人实测，不把演示账号的权限、数据和结果扩大到所有用户；不在正文逐例交代参考了哪个演示 |
| 第三方真实实践 | 重新组织当事人的需求、行动、产物与公开结果 | 保留必要归属，收入等自报事实不升级成独立核实，不复制原文的表达与叙事身份 |
| 拟议用途或组合方案 | 说明一种可尝试的做法，为读者打开用途 | 写成可以、计划或下一步；不能称为实测案例、已跑通流程或稳定交付 |

同一篇可以混用几种来源。普通功能举例直接讲怎么用，后台保存详细出处；本人实测与待尝试方案按真实状态写清。只有来源身份影响结论，或涉及当事人自报结果、收入与争议时，才在相关位置保留必要归属，不把正文写成逐条核验报告。

## 头脑风暴要比较读者收获

通常比较两三个实质不同的角度，而不只是换标题。每条路线简短写出：

- 这篇帮助谁，回答什么问题，标题能承诺什么。
- 最合适的开头与推进主线。
- 哪个案例担当主证据，其他案例补充什么。
- 资料或实操缺口，补齐是否值得。

按读者收获、材料支撑和可完成程度推荐一条。热度高、功能多、讲起来震撼不能单独成为推荐理由。用户指定了方向或说直接写，就推荐后自行推进；用户正在与我们讨论选题时，再把路线拿出来一起比较。不要每篇强制等待确认，也不要对已认可的标题和开头重新投票。

标题与开头按同一条读者承诺打磨：标题给出点开的理由，开头尽快拿具体痛点、动作或成果承接。为这两个入口保留足够的推敲，不把它们当作写完正文后随手补的包装；吸引力必须由材料支撑。

材料与角度会相互修正。案例在研究时就开始找，在头脑风暴时帮助选路线；不是先写好结论，再把案例当装饰贴进去。

## 围绕主线补案例和实操

对准备采用的案例，能说清以下内容即可：谁要解决什么问题，给了什么输入，AI 做了什么，最后出现什么结果，有什么图片或原始记录支撑。来源、视频时间点、时间口径和关键限制存入素材记录；普通科普不必逐项展示这张记录。

实操优先解决一个真实疑问，例如能否接到当前账号、能否读取指定资料、输出是否满足这次需求。有设备和授权、且测试能增加判断时就上手。不要为了写出“我也试了一下”去找没有代表性的任务；也不要在合理尝试失败后一直阻塞已经有材料支撑的科普。说明已确认的部分，余下选合适的官方或第三方案例。

每个案例有明确作用：解释一种新用途、展示成果、说明关键操作、体现投入或限定适用范围。作用相同又没有新增信息的案例合并或舍弃。一个长案例与几个短案例都可以成立，取决于这篇的承诺。

配图跟着用途选择。需要展示交互或结果变化时用短 GIF；静态输出用清晰截图即可。视频取产品界面与关键操作，不把讲解人、直播标题和无关字幕占进正文画面。GIF 的起点、中段和结尾都要检查，避免后面切回人像；图注解释操作与结果，后台保留来源时间点。原型、模拟数据等会影响理解的状态仍要交代。

## 先写文章，再按承诺检查

成稿前用简短的段落顺序确认主线，每段回答一个读者问题。科普要让人快速找到用途，教程要让操作接得上，事件文章要让后面的事实推进前面的疑问。不要为了统一格式把各类文章写成同一骨架。

冷读时检查：标题说“快速掌握”，正文有没有解释用途和开始方法；说“实测”，有没有真实输入与结果；说“机会”，有没有需求与服务对象支撑。技术词、功能清单和愿景没有替代这些答案。

再做表达取舍与扫读检查。逐段确认新增收益，逐句删改重复和空泛表达；保留必要解释、准确边界与有作用的情绪细节。最后只扫标题、小标题和加粗文字，看读者能否快速获得主要结论与做法。专业词先判断能否直接换成普通说法；操作名称或确有必要的概念再保留、解释，不能靠压缩把理解工作转嫁给读者。

最后按发布参考检查图片、图文复制和需要的封面。交付文章，另存素材与编辑记录；是否在公众号实际粘贴、上传或发布，按真实完成状态报告。

## OPCroad 中可借鉴的不同路线

- 知识库首篇：用户自己的经历与资源发布，先解释读者能得到什么；不能把作者历史经历变成所有文章都必备的开头。
- 人像提示词文章：具体图像问题 → 参考图拆解 → 可复制写法 → 技能使用。配图和提示承担教学，不必引入宏大趋势。
- AI 复刻与 REA：公开事件和第三方案例引出能力变化，再接作者自己的小范围尝试。适合事件推进，赚钱案例只服务当篇问题。
- WorkBuddy 接企微：个人群聊样本少，不能很好展示复杂办公痛点；用官方演示覆盖工作盘点、PPT、项目跟进、数据看板和原型，配本人已确认的接入入口。主目的是功能科普，整套知识库与专家组合仍是待搭建方案。
